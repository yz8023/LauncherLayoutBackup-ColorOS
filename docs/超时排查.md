# 为什么一直提示「请求超时，桌面进程无响应」

> 适用版本：v1.1.1 及以后。v1.1 及以前这个超时是**必然**会出现的，不是偶发。

## 一、现象

```
01:20:44  ──────── 打开 App ────────
01:20:46  ✅ 权限检测全部通过，进入主界面
01:21:01  ⚠️ 请求超时，桌面进程无响应
01:21:06  ⚠️ 请求超时，桌面进程无响应
...
```

注意关键细节：**第一步（权限检测）是通的**——说明模块注入成功、桌面进程活着、广播也能送达。
挂了的是**进入主界面之后的请求**。所以问题不是「模块没生效」，而是「之后的广播被系统压住了」。

## 二、根因（两个叠加）

### 1. 广播被排进「后台广播队列」（主因）

App 判定「桌面进程」是不是活着，靠的是跨进程广播：

```
模块 App  ──sendBroadcast──▶  系统桌面进程里的动态接收器
                            ◀──sendBroadcast──  再把结果回执给 App
```

`sendBroadcast()` 默认**没有** `FLAG_RECEIVER_FOREGROUND` 时，接收方如果处于后台/缓存状态，
这条广播就会被塞进系统的**后台广播队列（background broadcast queue）**。
这个队列是**串行 + 批处理 + 低优先级**的，Android 原生就要等好几秒，ColorOS 上叠加自家的
后台管理，十几秒才派发是常态。

时间线刚好对上：

| 时刻 | 发生了什么 |
|---|---|
| App 打开瞬间 | 桌面进程还是「刚被压到后台」状态，不算冷，第一条广播几十毫秒就送到了 → 权限检测通过 |
| 约 3 秒后 | App 已经在前台，桌面进程降级为 cached（ColorOS 还会再加一层 cgroup 冻结） |
| 之后的每个请求 | 全都被排进后台队列 → 我们 9 秒就判超时了 |

### 2. 首次超时没有重发

旧代码一次超时就直接报错并结束，没有给「第二条广播能把进程唤醒」的机会。
而实际上，第一条广播本身就会让系统把冻结的进程解冻，第二条通常立刻可达。

## 三、v1.1.1 的修法

| 改动 | 位置 | 作用 |
|---|---|---|
| 请求广播加 `FLAG_RECEIVER_FOREGROUND` | `BaseActivity.send()` | 走**前台广播队列**，绕开后台队列排队，通常几十毫秒送达 |
| 回执广播加 `FLAG_RECEIVER_FOREGROUND` | `Bridge.replyEx()` | 桌面明明处理完了、App 却还在等超时，就是因为回执也被排在后台队列 |
| 首次 3.5 秒没回音 → **自动重发一次**，再等 9 秒 | `BaseActivity.armTimeout()` | 覆盖「后台队列 + 进程被冻结」两种情况；重发本身就是一次唤醒动作 |
| 超时日志不再刷屏 | `BaseActivity.logTimeout()` | 同一时刻多个请求一起超时只写一条，并附带「其间另有 N 个请求超时」 |
| 超时日志带操作名 | 同上 | 直接看到是「读取备份列表」还是「恢复」超时，排查不用猜 |
| 新增「桌面连接诊断」 | 设置页 | 「测试连接」显示真实往返延迟；「唤醒桌面」用 root 把桌面短暂拉起来解冻后再测 |

## 四、怎么验证修好了

1. 安装 v1.1.1，打开 App 走到主界面。
2. 设置 → 桌面连接诊断 → **测试连接**。
   - 日志出现 `✅ 桌面进程响应正常，往返 XXX ms`
   - 正常值：**30 ~ 400 ms**（冷启动第一条可能 1~2 秒，属正常）
   - 若显示「往返偏慢，本次是重发后才送达」→ 说明仍被后台队列影响，但已经能兜住，功能可用。
3. 回到首页下拉刷新，或点备份列表，不再出现大段超时即可。

## 五、如果「测试连接」完全没回包

说明不是慢，是根本没人接。按顺序排查：

1. **LSPosed 里作用域是否勾选了「系统桌面」**（`com.android.launcher`）。
2. **模块是否启用**，且安装后是否重启过一次手机（LSPosed 首次激活需要）。
   > 之后的模块小版本更新**不需要再重启手机**：设置页 →「热重载：快速重启桌面」即可，
   > 等价于让桌面进程重新加载模块，比重启手机快得多。
3. 用 root 确认进程在：`adb shell su -c "pidof com.android.launcher"` 应输出 PID。
4. 看 LSPosed 日志里有没有 `LLB: 桥已就绪，广播接收器已注册（uid=...）`
   —— 有这行说明注入正常；没有则是注入失败（十有八九是作用域/未启用）。
5. 仍不行：设置页 →「Root 强制停止桌面」，系统会自动把桌面重新拉起并重新注入。

## 六、已知与系统行为有关的限制

- ColorOS 会主动清理/冻结后台进程，桌面也不例外。**任何时候**它被深冻结，第一次请求都可能慢一拍；
  重发机制会自动兜住，所以看到「已自动重发 1 次」不代表坏了。
- 恢复操作是先杀桌面再从进程外覆盖数据库，桌面重启期间（约 3~8 秒）所有请求都会超时，
  这是**正常的**，等桌面起来后会自动恢复。
